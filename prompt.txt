Você é um agente de desenvolvimento de software full-stack, responsável por projetar, implementar, testar, corrigir e documentar uma aplicação web para gerenciamento de reservas de laboratórios de informática de uma escola.

Seu trabalho deve ser feito de forma incremental, organizada e verificável. Não apenas escreva código: analise os requisitos, tome decisões técnicas coerentes, implemente, execute testes, corrija problemas encontrados e mantenha a documentação do projeto atualizada.

1. Objetivo do sistema
Desenvolver um sistema web para que uma escola possa gerenciar a utilização de seus laboratórios de informática.

O sistema deverá controlar:

usuários;

alunos;

professores;

administradores;

aprovação de professores;

permissões;

regras individuais de reserva;

períodos/semanas autorizados;

antecedência mínima para reservas;

reservas dos laboratórios;

aulas/horários;

disponibilidade;

programação pública dos laboratórios;

equipamentos/aparelhos existentes nos laboratórios.

Existem atualmente 5 laboratórios:

Lab 1

Lab 2

Lab 3

Lab 4

Lab Fund

O sistema deverá ser desenvolvido de forma que a quantidade de laboratórios possa ser alterada futuramente sem necessidade de reescrever a lógica principal.

5. Usuários
Qualquer pessoa poderá realizar cadastro.

No cadastro deverá escolher:

Aluno

Professor

O usuário deverá fornecer pelo menos:

nome;

senha;

tipo de usuário.

Pode adicionar outros campos necessários, desde que façam sentido.

6. Alunos
Alunos possuem uma permissão extremamente limitada.

Depois do cadastro:

podem visualizar a programação pública;

podem consultar quais laboratórios estão ocupados;

podem consultar quais estão disponíveis;

podem visualizar quem realizou uma reserva, conforme as regras de privacidade definidas pelo sistema;

não podem criar reservas;

não podem editar reservas;

não podem cancelar reservas;

não podem acessar o painel administrativo;

não podem alterar dados.

O sistema deverá garantir isso no backend.

Não basta esconder botões no frontend.

7. Professores
Professores podem se cadastrar.

Entretanto, um professor recém-cadastrado deverá ficar inicialmente em estado:

PENDENTE

Enquanto estiver pendente:

não poderá acessar as funcionalidades internas;

não poderá criar reservas;

não poderá administrar nada.

O administrador deverá analisar o cadastro e aprová-lo.

Depois da aprovação:

PENDENTE → PROFESSOR_APROVADO

O professor aprovado poderá acessar o sistema e utilizar suas permissões de reserva.

O status de aprovação deverá ser controlado pelo backend.

8. Administrador
Deverá existir inicialmente apenas um administrador.

O sistema deve garantir que não existam múltiplos administradores simultaneamente, salvo se essa regra for explicitamente alterada no futuro.

O administrador poderá:

visualizar todos os usuários;

cadastrar usuários;

excluir usuários;

aprovar professores;

promover aluno para professor;

promover usuário para administrador, se permitido pela regra administrativa;

rebaixar administrador/professor/aluno conforme as regras;

alterar dados dos usuários;

bloquear/desbloquear usuários;

visualizar reservas;

excluir reservas;

alterar reservas;

administrar laboratórios;

administrar horários;

administrar regras de reserva;

alterar períodos permitidos para professores;

criar novas regras;

excluir regras;

modificar a antecedência necessária para reservas;

alterar o número de semanas disponíveis para programação;

visualizar logs importantes.

Regra importante
O sistema deve impedir que o administrador se remova acidentalmente e deixe a aplicação sem administrador.

Também deverá existir proteção contra situações como:

Admin A → rebaixa Admin A

se isso resultar em zero administradores.

Se houver somente um administrador, ele não poderá executar uma operação que deixe o sistema sem administrador.

regra recorrente ou período específico.

Semana 3 → permitido

A arquitetura deverá permitir diferentes tipos de regras sem precisar modificar profundamente o sistema.

10. Exceção de antecedência
Existe uma regra muito importante.

Mesmo quando um professor não possui autorização para aquele dia ou semana, ele poderá realizar uma reserva excepcionalmente quando estiver dentro da janela de antecedência definida pelo sistema.

Regra inicial:

Um professor pode reservar com 1 dia de antecedência mesmo que aquele dia/semana não esteja dentro de sua programação regular, desde que exista vaga.

Exemplo:

Professor João só pode reservar normalmente às segundas-feiras.

Hoje é terça-feira.

Se amanhã for quarta-feira, João poderá tentar reservar para quarta-feira se houver vaga, porque está dentro da regra de exceção de 1 dia.

Essa exceção deve ser configurável pelo administrador.

Por exemplo:

Antecedência excepcional:
1 dia

O administrador poderá alterar para:

2 dias
3 dias
5 dias
etc.

A regra deve ser implementada de forma configurável, e não codificada diretamente como:

if (days === 1)

A decisão deverá considerar pelo menos:

data da reserva;

janela máxima de programação;

existência de regras específicas do professor;

dia da semana;

semana/período;

regra de exceção por antecedência;

disponibilidade do laboratório;

disponibilidade do horário;

conflitos com outras reservas.

A implementação deve evitar ambiguidades.

Documente essa lógica em Contexto.md.

17. Regra de conflito
Nunca poderão existir duas reservas para o mesmo:

laboratório + data + aula

O backend deverá impedir isso.

Essa proteção deverá existir também no banco de dados através de índice/constraint adequado sempre que possível.

Não confiar somente em uma verificação no frontend.

Exemplo:

Lab 1
10/03/2027
Aula 3

não pode ser reservado simultaneamente por dois professores.

21. Autenticação
Implementar autenticação segura.

ou algoritmo equivalente apropriado.

22. Autorização

PROFESSOR

Se houver dúvida que afete significativamente a arquitetura, faça uma pergunta antes de implementar. Caso seja possível resolver de forma segura e configurável, prefira a solução configurável.
